# ملاحظات التشخيص المعماري الجذري لوكيل Kimo

**التاريخ:** 18 أغسطس 2026

**النطاق:** الصوت، الصور، الملفات، ملفات Excel/CSV الكبيرة، وعلاقة هذه القنوات بدورة ReAct وطبقة المزودات والتاريخ المحلي.

**قيد صريح:** هذه الوثيقة تشخيص فقط. لم تُنفذ في هذه الجولة أي إصلاحات كود أو تغييرات سلوكية.

## الحكم الأولي

المشكلة ليست مجموعة أعطال مستقلة في زر الصوت أو منتقي الملفات أو Prompt النموذج. التطبيق يملك عدة مسارات إدخال منفصلة، ثم يحاول تحويلها في نقطة متأخرة إلى رسالة Chat واحدة. لذلك لا توجد حمولة مستخدم معيارية تمثل النص والصوت والصورة والملف والنية المرتبطة بها ككيان واحد قابل للتتبع وإعادة التشغيل.

النتيجة العملية هي أن كل قناة تفشل بطريقة مختلفة: الصوت يُرفض قبل الإرسال أو يُرسل كـBase64 داخل رسالة؛ الملفات تُحفظ كمسارات محلية ويُعطى النموذج معرفاً نصياً؛ الصور لا تملك مساراً assistant-side أصلاً؛ وExcel يُقرأ كاملاً في الذاكرة ثم يُقص أو يُحد إلى عينة/8000 صف. هذه ليست فجوة Prompt، بل غياب طبقة ingestion وartifact processing موحدة.

## مسار الإدخال الحالي كما هو فعلياً

```text
UI text ───────────────┐
UI files ── save URI ───┼─> SQLite agent_attachments + textual hint ──> read_uploaded_file/import tool
UI audio ─ read Base64 ─┘                                      │
                                                               ├─> provider Chat message
UI image ── لا يوجد مسار assistant مستقل واضح ──────────────────┘

Excel/CSV ─> read full file/base64 ─> ExcelJS arrays ─> preview أو workspace rows
```

هذا المسار يخلط أربعة أشياء يجب فصلها: **الأصل المرفق**، **المعالجة**، **المعرفة المستخرجة**، و**قرار الوكيل**. حالياً الوكيل يرى ملفاً على شكل اسم ومعرف ونصيحة، ولا يملك عقداً يضمن أن الملف فُتح أو فُكك أو فُهم قبل أن يتصرف.

## الاستنتاجات المرحلية

أولاً، فشل الصوت ليس مجرد نقص موديل. هناك حد حجم محلي، وتمثيل Base64 كبير داخل طلب Chat، ورفض كامل لبعض العائلات، وعدم وجود تفريغ كخدمة محلية مستقلة. لذلك تغيير اسم موديل أو إضافة regex جديد لن يحل المسار.

ثانياً، فشل الصور بنيوي في واجهة الإدخال وفي العقد الداخلي معاً. وجود دعم vision في بعض الموديلات لا يعني أن Kimo يستطيع استقبال صورة من المستخدم، حفظها، معاينتها، ربطها بعقار أو عرض، ثم إعادة استخدامها في جولة لاحقة.

ثالثاً، فشل الملفات ليس في زر DocumentPicker فقط. الملف يُسجّل كـURI محلي، ثم يعتمد الوكيل على استدعاء لاحق باسم الملف. لا توجد حالة معالجة مستقلة مثل uploaded → validated → parsed → indexed → linked، ولا checksum أو نتيجة parsing قابلة لإعادة الاستخدام.

رابعاً، Excel الكبير يعالج كحمولة واحدة في الذاكرة. حد 8000 صف هو قرار حماية محلي وليس حلاً للمشكلة؛ كما أن `sheetToTableData` يبني المصفوفة كاملة قبل أخذ العينة، ولذلك قد يحدث الضغط قبل الوصول إلى الحد نفسه. لا توجد دلالة واضحة للصفوف المرفوضة أو الأعمدة غير الصالحة أو الاستئناف.

خامساً، طبقة المزودات تحاول حماية التطبيق من 400 عبر fail-closed، لكنها تستخدم مصدراً غير موحد للقدرات: catalog metadata عند توفره، وإلا regex/static assumptions. هذا جيد لمنع بعض الطلبات الخاطئة، لكنه لا يبني قدرة multimodal حقيقية ولا يفسر للمستخدم مسار التحويل أو fallback.

## ما يجب حسمه قبل أي إصلاح

1. هل Kimo وكيل محادثة multimodal، أم مدير عمليات محلي يستعين بنماذج متخصصة؟ القرار يغير المعمارية بالكامل.
2. هل يجب أن تعمل الصور والصوت مع كل مزود، أم أن المطلوب هو fallback محلي موحد: تفريغ الصوت إلى نص، واستخراج الصور إلى وصف/حقول، ثم إرسال ناتج موحد للنموذج؟
3. هل Excel جزء من سياق المحادثة أم مصدر بيانات يجب إدخاله في pipeline مستقل قابل للاستئناف؟ التعامل معه كسياق Chat غير قابل للتوسع.
4. هل التطبيق يقبل التخزين المحلي المؤقت للـartifacts والمعرفة المشتقة، أم يجب حذف كل وسيط بعد المهمة؟ لا يمكن بناء lifecycle موثوق دون هذا القرار.

## قرار تشخيصي مؤقت

لا ينبغي تنفيذ إصلاحات جديدة في `AssistantScreen.tsx` أو `files.ts` أو `providers.ts` منفردة. طبقة الإدخال الحالية يجب أن تُعاد صياغتها حول عقد موحد للحمولة، ومدير artifacts محلي، ومعالجات deterministic للوسائط والملفات، وطبقة قدرة مزودين مستقلة عن أسماء النماذج. بعد تثبيت ذلك فقط تصبح إصلاحات الواجهة والمزودات ذات معنى.
