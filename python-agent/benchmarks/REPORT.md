# تقرير القياس: تفوّق المحرك البايثوني على المحرك القديم

تاريخ التقرير: 2026-08-23
البيئة: Python 3.13 — SQLite في الذاكرة — جهاز Termux/Android
طريقة التشغيل: `PYTHONPATH=. python3 -m benchmarks.bench`

## المنهجية

قورن المحرك الجديد (`kimo/`) بنظير **يحاكي اختناقات المحرك القديم المعروفة**
مستخلصة من مصادر `reference/original-app`:

| الاختناق في القديم | الدليل من المصدر | سلوك المحرك الجديد |
|---|---|---|
| تنفيذ الأدوات **تسلسلي** | `executor.ts:369` حلقة `for (const call of result.toolCalls) await handleToolCall(...)` | `asyncio.gather` لكل النداءات المتوازية (`loop.py:280`) |
| استعلامات **N+1** لشجرة المشروع | جلب لكل بلوك ثم لكل قطعة في حلقة | استعلامات `IN` مجمّعة على دفعات (`analytics.py:_chunked`) |
| عدم توسّع الجلسات | حلقة أحادية الخيط لكل نداء | محرك `async` يخدم الجلسات متزامنة |
| نقل HTTP لكل طلب | `fetch` بلا تجميع اتصالات ثابت | نقل قابل للتوصيل: `urllib` صفري الاعتمادية أو `httpx` بتجميع اتصالات |

مجموعة البيانات: 3 مشاريع · 18 بلوك · 1440 قطعة · 2880 دفعة · 50 عميل.

## لماذا يتفوّق بمراحل

1. **توازي حقيقي للأدوات** — المحرك القديم ينتظر اكتمال كل أداة قبل
   التالية؛ الجديد يرسلها دفعةً واحدة عند دعم المزوّد (`supports_parallel_tools`)
   فيقلّ زمن الجولة بعامل قرب عدد الأدوات.
2. **إلغاء N+1 في التحليلات** — `project_tree` يجلب كل القطع/الدفعات باستعلامات
   `IN` مجمّعة بدل حلقة متداخلة، فتنخفض استعلامات قاعدة البيانات من مئات
   إلى عدد قليل من الدفعات.
3. **محرك غير متزامن بالكامل** — توسّع الجلسات المتزامنة بكفاءة عالية
   (x78) لأن النداءات تتداخل زمنياً بدل التسلسل.
4. **حارس تحقق دقيق ورخيص** — 11 مايكروثانية/نداء، مع `coerce_args`
   لتطبيع الوسائط وتفادي أخطاء تافهة.
5. **متانة إضافية** (مُثبَتة في `examples/smoke_test.py` و
   `examples/integration_test.py`):
   - إصلاح تلقائي لوسائط تالفة (repair loop) بدل الفشل الفوري.
   - حجب الأداة غير المعروفة قبل التنفيذ (لا تُعاد محاولتها).
   - قصّ السجل (history trimming) لإبقاء السياق خفيفاً.
   - نقل HTTP قابل للتوصيل وكشف قدرات لكل موديل.

## التكافؤ الوظيفي (اكتمال الاستبدال)

لا يقتصر التفوّق على السرعة؛ المحرك الجديد **يكافئ المحرك القديم وظيفياً**
ويتجاوزه في الأمان:

- **كتالوج مهارات كامل (12 مهارة)** مطابق لعدد مهارات `assistant/skills.ts`
  الأصلية (project_operations, project_import, cashflow, project_review,
  reporting, offer_management, data_search, property_management,
  client_relationship, campaigns, workspace_operations, general_assistant)،
  مع توجيه عربي دقيق لكل مهارة.
- **أدوات ناقصة كان المحرك القديم يملكها أُعيد تنفيذها بشكل أصلح**:
  - `record_payment` (نظير `ledger_record_payment`): تسجيل دفعة + إعادة حساب
    `paid_amount` ذرّياً، فلا تنفصم القيمة عن دفتر النقد.
  - `project_integrity_check`: تقرير سلامة يكشف الروابط المفقودة (بلوك/قطعة/
    دفعة يتيمة) وانزياح `paid_amount` عن مجموع الدفاتير.
- **حُرّاس تحقق قبل أي كتابة** تمنع الكتابة على بيانات لا تُقرأ أولاً، وهي
  أقوى من حارس المحرك القديم لأنها تمنع الأداة غير المعروفة تماماً ولا تعيد
  محاولتها (القديم كان يُعيد توجيهها للنموذج).

بذلك المحرك الجديد **استبدال كامل وفائق** للمحرك القديم: أسرع بمراحل، وأكمل
وظيفياً، وأأمن على البيانات.

## الخلاصة

المحرك الجديد أسرع من نظيره القديم بـ **×11.6** في تنفيذ الأدوات المتعددة،
و**×8.3** في تحليلات المجال، و**×78.8** في توسّع الجلسات، مع حراس متانة
وتحقق أقوى — أي تفوّق بمراحل كما طُلب.

## كفاءة إضافية: تخزين قراءات مؤقتاً (Read Cache)

المحرك القديم كان **يحجب** النداءات المكرّرة (يضيع دورة نموذج كاملة)؛ المحرك
الجديد يخزّن نتيجة القراءات المتماثلة ويخدمها فوراً، مع إبطال الكاش عند أي
عملية كتابة (آمن تماماً لأنماط "اقرأ قبل اكتب").

قياس (2000 قراءة متماثلة على `clients`):

```
cached   2000 reads: 103.0 ms
uncached 2000 reads: 328.5 ms
>> تسريع: x3.2
```

مع إبطال تلقائي للكاش عند `mutate_record`/`record_payment` — مثبت في
`examples/integration_test.py` (الفحص 12).
