# تقرير جاهزية كيمو الإنتاجية

## الملخص التنفيذي

تم تحويل كيمو من طبقة محادثة تعتمد على تعليمات عامة وأحداث واجهة إلى نواة وكيل محلي ذات دورة تشغيل قابلة للتدقيق. لا تزال هذه العملية تطويراً مستمراً وليست ادعاءً بأن النظام وصل إلى اكتمال مطلق، إلا أن الحدود الأساسية للوكيل أصبحت فعلية داخل الكود وليست مجرد وعود في prompt.

أصبح كيمو يميز بين التحية والمحادثة العامة والطلب التنفيذي، يختار مهارة متخصصة، يعرض أدوات ضمن نطاق تلك المهارة، يقرأ البيانات المحلية قبل الكتابة، يفرق بين إنشاء العقار وتحديثه والالتباس، ويمنع إعلان الإتمام دون نتيجة أداة ناجحة ودليل محفوظ. كما أصبح بإمكانه استقبال مرفقات المستخدم بمعرفات ثابتة، ثم ربطها بالعقار أو العرض المقصود ضمن جلسة المستخدم دون حذف الأصل.

## دورة التشغيل الموحدة

تبدأ الدورة بتقييم النية. الرسائل العامة لا تنشئ TaskRun ولا تعرض بطاقة مهام وهمية. أما الطلب التنفيذي فينشئ تشغيلًا محليًا له حالات وانتقالات مقيدة، ثم يختار المهارة المناسبة ويكشف للموديل الأدوات المسموحة فقط. بعد ذلك تُقرأ السجلات ذات الصلة، وتُجرى المعاينة، ويُسأل المستخدم عند الالتباس أو عند وجود تغيير حساس، ثم تُنفذ الكتابة وتُقرأ النتيجة مرة أخرى وتسجل الأدلة.

| المرحلة | السلوك الإنتاجي المطبق |
|---|---|
| فهم الطلب | تصنيف conversation أو execution مع درجة ثقة وأسباب قرار |
| اختيار المهارة | توجيه متخصص لإدارة العقارات والعملاء والعروض والمشاريع والبحث والتقارير |
| نطاق الأدوات | قائمة الأدوات التي يراها الموديل تطابق الحارس التنفيذي |
| حالة التنفيذ | TaskRun محلي بحالات running وawaiting_user وverifying وcompleted وfailed وcancelled |
| السلامة | منع الانتقالات غير المسموحة ومنع completed دون دليل أداة ناجح |
| التحقق | سجل أدلة متراكم لنتائج الأدوات وقراءة بعدية للكيان |
| التعافي | تسجيل الفشل والإلغاء وعدم ترك المهمة في running بعد انقطاع المزود |

## إدخال تفاصيل عقار مع وسائط

أضيف مسار `property_change_preview` لمعاينة البيانات قبل الكتابة. يبحث المسار في قاعدة البيانات المحلية باستخدام المعرف والاسم والعنوان وأرقام التواصل، ثم يعيد إحدى الحالات الثلاث: `create` عند عدم وجود مطابقة موثوقة، أو `update` عند وجود عقار مطابق، أو `ambiguous` عند وجود أكثر من احتمال أو نقص هوية أساسية.

لا يقترح المسار إنشاء سجل من بيانات فارغة أو من معرف غير موجود. ويصنف التغييرات الحساسة مثل السعر والحالة والعنوان وبيانات المالك والدلال على أنها عالية المخاطر وتعيد `requiresApproval=true`. أضيف أيضاً `property_intake_apply` كمسار موحد يعيد المعاينة قبل التنفيذ، يوقف الالتباس، يطلب موافقة صريحة للتغييرات الحساسة، ينفذ الإنشاء أو التحديث، ثم يربط المرفقات المطلوبة ويعيد نتيجة موحدة.

## نقل الوسائط

تُحفظ المرفقات المرسلة مع الرسالة في `agent_attachments`، ويُضاف معرف المرفق إلى سياق الرسالة حتى لا يعتمد كيمو على اسم الملف وحده. أضيف جدول `entity_media` لعلاقة مستقلة بين المرفق والكيان، مع دعم `property` و`offer`، كما أضيف حقل `media` إلى العروض مع migration آمن.

| الحالة | السلوك |
|---|---|
| إرفاق الوسيط بعقار | تحديث سجل العقار وإضافة asset إلى media وإنشاء entity_media link |
| إرفاق الوسيط بعرض | تحديث سجل العرض بالطريقة نفسها |
| تكرار نفس الربط | إرجاع الرابط الموجود دون إنشاء نسخة أخرى |
| مرفق غير موجود | فشل مفهوم دون كتابة |
| أكثر من ملف بالاسم نفسه | طلب استخدام الاسم الكامل أو المعرف |
| هدف غير موجود | فشل مفهوم دون نقل |
| جلسة مختلفة | يمنع الربط عند تمرير session scope |
| حذف الأصل | لا يحدث تلقائياً؛ النقل ربط منطقي قابل للمراجعة |

## المزودات والنماذج

أصبح تصنيف المزود يمرر `providerId` الحقيقي إلى حلقة التنفيذ بدلاً من معاملة كل المزودات كـ custom. وتستخدم طبقة LLM ملف قدرات يحدد دعم الأدوات والبث وحقول الرموز وخيارات البث. لا تُرسل `tools` إلى مزود أو نموذج لا يعلن دعمها.

تم تصنيف أخطاء النقل إلى network وtimeout وrate_limit وserver وinvalid_request وauth وparse. تعاد المحاولة فقط للأخطاء المؤقتة أو ضغط الطلبات أو الخادم، بينما لا تعاد أخطاء 400 أو بيانات الاعتماد عشوائياً. كما طُبّع tool-call ID إلى صيغة مستقرة، وحُفظت الحقول الإضافية التي تحتاجها بعض البوابات مثل `thought_signature`.

## منع التكرار والصلاحيات

أصبح إنشاء العقار والعميل idempotent وفق مفاتيح طبيعية محلية معقولة. عند إعادة إرسال نفس الطلب لا ينشئ كيمو سجلاً مكرراً، بل يعيد المعرف الموجود مع علامة duplicate. وبالنسبة للأدوات، توجد بوابة تحقق مركزية للحقول والأنواع، وحارس صلاحيات يطابق أدوات المهارة المعروضة مع الأدوات المسموحة في التنفيذ.

## الاختبارات والتحقق

نجحت فحوص TypeScript وESLint الصارم واختبارات العقود والمعمارية والثوابت الحالية، بما في ذلك اختبارات التخزين الآمن، التذكيرات، علاقات العروض، الاستيراد المكاني، المرفقات، التحديث الجزئي، وسلامة قاعدة البيانات الفارغة. كما نجح تجميع Expo Web من الفرع الحالي.

أضيفت اختبارات مستقلة لعقد ربط الوسائط، وموجه النوايا، وتصنيف أخطاء المزودات، وحالة TaskRun، وسلوك لوحة المهام. وتشمل اختبارات المزودات التحقق من أن 429 و5xx قابلة للتعافي، بينما 400 و401 لا تُعاد تلقائياً.

## حالة الإدخال الصوتي

تم توثيق الإدخال الصوتي في مسار مستقل حتى لا يقطع إعادة بناء الوكيل. لم يُدخل اعتماد صوتي غير مكتمل إلى الفرع الحالي. بعد استقرار دورة الوكيل، يمكن تنفيذ التسجيل والمعاينة والتحويل إلى رسالة فوق هذه العقود، مع قائمة ثابتة توضح دعم كل مزود ونموذج بدلاً من افتراض الدعم.

## الحالة النهائية للفرع

الفرع هو `production-hardening-local`، وآخر commit برمجي موثق هو `9117202`، ويتضمن إصلاح lint الذي أوقف أول بناء APK بعد إضافة workflow الإدخال الموحد. بناء APK الموقّع الأخير قيد التنفيذ على GitHub Actions، بينما نجحت قبله كل خطوات TypeScript وLint والاختبارات وتهيئة Android. رابط المتابعة هو:

[GitHub Actions — Build Signed APK](https://github.com/adibadm409-eng/property-manager-app/actions/runs/31974827494)

## الحدود الصادقة المتبقية

لا يزال يلزم اختبار ميداني على أجهزة Android مختلفة، خصوصاً سلوك لوحة المفاتيح والإشعارات المحلية وفتح وسائط الفيديو. كما ينبغي تنفيذ اختبارات تكامل حقيقية مع كل مزود مدعوم، لأن ملف القدرات يمنع الطلبات غير المناسبة لكنه لا يستطيع ضمان أن endpoint مخصص يطبق مواصفاته بشكل صحيح. كذلك يحتاج الإدخال الصوتي إلى تنفيذ مستقل بعد تثبيت طبقة الوكيل الحالية.

> معيار النجاح النهائي ليس أن يكتب كيمو رداً مقنعاً، بل أن تكون كل عملية مهمة قابلة للفهم والمراجعة والإثبات، وأن يتوقف عندما لا يملك هوية أو صلاحية أو دليلاً كافياً.
