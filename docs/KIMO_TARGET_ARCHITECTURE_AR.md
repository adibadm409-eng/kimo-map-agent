# المعمارية المستهدفة لوكيل كيمو

## المبدأ الحاكم

كيمو ليس واجهة محادثة تستدعي دوالاً عشوائياً، وليس prompt طويلاً يحاول تعويض غياب النظام. كيمو هو **نظام تشغيل مهام محلي** يستخدم نموذجاً لغوياً كطبقة اقتراح واستدلال، بينما تبقى الحالة والصلاحيات والتحقق والتنفيذ داخل التطبيق وقاعدة بيانات SQLite.

> لا يجوز للنموذج أن يعلن نتيجة لم يثبتها سجل التنفيذ، ولا يجوز لواجهة المستخدم أن تعرض حالة لا يملكها كائن المهمة المحلي.

## الطبقات الإلزامية

| الطبقة | مسؤوليتها الوحيدة | لا يجوز لها |
|---|---|---|
| واجهة المحادثة | عرض الرسائل وحالة التشغيل وطلبات القرار | إنشاء خطة أو تخمين نجاح أداة |
| موجه النوايا | تصنيف الرسالة وتحديد درجة الثقة واختيار مسار أولي | تنفيذ قراءة أو كتابة |
| المهارة | سياسة العمل: المدخلات، الأدوات المسموحة، المخاطر، التحقق والتعافي | تجاوز بوابة الصلاحيات أو تعديل SQLite مباشرة |
| TaskRun | الحالة الرسمية للمهمة، الخطوات، الانتقالات، الاستئناف والإلغاء | تفسير نص النموذج أو تنفيذ أداة بنفسه |
| بوابة الأدوات | التحقق من arguments، التفويض، idempotency، التنفيذ، توحيد النتيجة | تمرير arguments غير صالحة إلى domain code |
| المجال وقاعدة البيانات | قواعد العقارات والمشاريع والعروض والمالية والمعاملات | معرفة تفاصيل المزود أو فرض صياغة prompt |
| محول المزود | تطبيع الرسائل والأدوات والبث والمهل والأخطاء حسب المزود والموديل | اتخاذ قرار عقاري أو تعديل البيانات |
| سجل التدقيق والأدلة | تسجيل ما قُرئ وما كُتب وما تحقق منه | أن يكون بديلاً عن الحالة الرسمية للمهمة |

## دورة حياة المهمة

كل طلب تنفيذي يمر بالحالات التالية، ولا يسمح النظام بانتقال عشوائي بينها:

```text
received
  → classified
  → proposed
  → awaiting_user       (عند نقص معلومة أو طلب موافقة)
  → running
  → verifying
  → completed
```

وتوجد مسارات فشل واضحة:

```text
running → failed
running → cancelled
verifying → failed
awaiting_user → cancelled
```

حالة `completed` ليست مرادفاً لوصول نص من النموذج. لا تُقبل إلا عند وجود نتيجة نهائية، ونتيجة أداة أو قراءة تحقق مناسبة، وعدم وجود أخطاء غير معالجة. أما الرد النصي العام فينتهي كرسالة محادثة لا كمهمة مكتملة.

## عقد الأداة

يجب أن تكون الأداة قابلة للفحص قبل التنفيذ، وأن تعيد نتيجة معيارية بعده:

```ts
interface ToolContract {
  name: string
  version: string
  risk: 'read' | 'write' | 'destructive'
  inputSchema: Schema
  outputSchema: Schema
  idempotency: 'none' | 'keyed' | 'natural-key'
  requiresApproval: boolean
  verification: string[]
}

interface ToolResult<T = unknown> {
  ok: boolean
  code: string
  summary: string
  data?: T
  evidence: Evidence[]
  retryable: boolean
  needsUser: boolean
  mutation?: { operation: string; affectedIds: string[]; idempotencyKey?: string }
}
```

الرسالة النصية وحدها لا تكفي كعقد إخراج. يجب أن يستطيع TaskRun معرفة هل نجحت العملية، وما السجلات المتأثرة، وما القراءة التي تثبت النتيجة، وهل يمكن تكرارها بأمان.

## عزل المزودات والنماذج

يُسمح للمزودات بتقديم قدرات مختلفة، لكن لا يُسمح لها بتغيير منطق المهمة. لذلك يمر كل طلب عبر ملف قدرات يحدد على الأقل: دعم الأدوات، دعم البث، صيغة tool-call ID، حقل حد الرموز، شكل الخطأ، طريقة المصادقة، وحدود السياق. إذا لم تثبت القدرة، لا يرسل المحول الخيار إلى المزود.

عند خطأ 400، لا تعاد المحاولة العمياء. يصنف الخطأ أولاً إلى: schema، model capability، message history، authentication، أو request size. ثم يُسمح بمسار تعافٍ محدد، مثل تنظيف التاريخ، تقليل الخيارات، تغيير حقل الرموز، أو طلب قرار المستخدم. أما إعادة نفس body خمس مرات فليست تعافياً.

## الذاكرة المحلية

يجب فصل أربعة أنواع من الذاكرة:

| النوع | المحتوى | العمر |
|---|---|---|
| سياق المحادثة | الرسائل التي يحتاجها النموذج لفهم الحوار | حسب سياسة نافذة السياق |
| حالة TaskRun | الخطوة والحالة والانتقال الحالي | حتى إغلاق المهمة وأرشفتها |
| سجل التدقيق | من طلب، ماذا قرأ، ماذا كتب، ومتى | طويل الأجل محلياً |
| الأدلة | نتائج القراءة التي تثبت الأرقام والروابط | مرتبطة بالمهمة والنتيجة |

لا يجوز استخدام `agent_runtime_events` وحده كحالة رسمية؛ فهو سجل عرض. الحالة الرسمية يجب أن تكون قابلة للقراءة والاستعلام، ولذلك أضيف `agent_task_runs` و`agent_task_events` كخطوة أولى في هذا الاتجاه.

## سياسة الأسئلة والافتراضات

يسأل كيمو عندما يكون النقص مؤثراً على صحة البيانات أو سلامة العملية. يستخدم افتراضاً آمناً فقط عندما لا يغير المعنى ولا يسبب كتابة خاطئة. ولا يختار عقاراً أو عميلاً أو مبلغاً أو تاريخاً من عنده. في العمليات التدميرية، تكون الموافقة صريحة ومحددة بالعناصر المتأثرة.

## معيار الاختبار

الاختبارات لا تكتفي بأن النموذج أعاد JSON. يجب اختبار النظام عند: تحية، طلب غامض، مشروع أرض متعدد البلوكات والقطع، مشروع مبنى متعدد الطوابق، تسجيل قسط مع دليل، عرض بيع مرتبط، عرض شراء غير مرتبط ثم ربطه، تعديل جزئي، فشل 400، timeout، تكرار نداء أداة، إغلاق التطبيق أثناء المهمة، وعودة المستخدم لاستئنافها.

## ترتيب التنفيذ

سيتم تثبيت الحدود والعقود أولاً، ثم توسيع المهارات، ثم إدخال التحقق والتعافي، وبعد ذلك تحسين العرض. الإدخال الصوتي وقائمة قدرات الصوت طبقة إدخال تترجم إلى رسالة أو مرفق؛ لا تملك صلاحية تغيير دورة المهمة ولا تتقدم على إصلاحها.
