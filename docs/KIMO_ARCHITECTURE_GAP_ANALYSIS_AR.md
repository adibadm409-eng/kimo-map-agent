# تقييم فجوة كيمو المعمارية

## الخلاصة التنفيذية

كيمو في وضعه الحالي ليس «وكيلًا عالميًا» بالمعنى الإنتاجي الكامل، لكنه يمتلك نواة مفيدة: حلقة استدعاء أدوات، مهارات، سجل أحداث، تخزين محلي، وبعض حواجز التكرار. المشكلة الأساسية ليست غياب المزايا، بل أن هذه المزايا غير موحّدة داخل **نموذج تشغيل واحد قابل للإثبات**. لذلك تظهر فجوة بين ما تعرضه الواجهة وما حدث فعليًا، وبين عقد الأداة التي يفهمها النموذج وما تقبله المزودات المختلفة، وبين الخطة المخزنة وحالة المهمة الحقيقية.

المعيار المستهدف ليس أن يجيب النموذج بشكل جميل، بل أن يكون كل قرار قابلًا للتفسير، وكل كتابة قابلةً للتحقق، وكل فشل قابلًا للتصنيف والتعافي، وكل نتيجة قابلةً لإعادة القراءة من قاعدة البيانات المحلية.

## تشخيص الوضع الحالي

| المجال | الموجود حاليًا | الفجوة الإنتاجية الحرجة |
|---|---|---|
| دورة التنفيذ | حلقة ReAct تعتمد على جولات الأدوات وتبث أحداثًا مرئية | لا يوجد كائن تشغيل موحد يفرض انتقالات الحالة ويمنع الإعلان قبل تحقق النتيجة |
| الخطط | `AgentPlan` بخطوات وحالات | الخطة تُنشأ قبل إثبات أن الرسالة مهمة تنفيذية، وتُخزن أحداثها دون سياسة عمر أو ملكية واضحة |
| المهارات | مطابقة كلمات ومهارة افتراضية عامة | المطابقة ليست نية متعددة الطبقات ولا يوجد تقييم ثقة أو تفويض صلاحيات لكل مهارة |
| الأدوات | أدوات كثيرة بعقود وصفية ومعالجات مباشرة | لا توجد طبقة موحدة لـ schema validation، التطبيع، التفويض، idempotency، ونتيجة قابلة للآلة |
| المزودات | واجهة OpenAI-compatible مع معالجة جزئية لـ SSE وحقول Gemini | اختلافات `tools`, `stream_options`, `max_tokens`, tool-call IDs، وحقول التفكير لا تزال معرضة لأخطاء 400 |
| الذاكرة | رسائل، brain ops، وruntime events في SQLite | لا يوجد فصل صارم بين ذاكرة المحادثة، حالة المهمة، سجل التدقيق، ونتيجة التنفيذ |
| التحقق | بعض أدوات integrity وقراءة لاحقة في مهارات معينة | التحقق ليس سياسة مركزية ملزمة لكل كتابة، ولا يوجد إثبات نتيجة قبل إعلان الاكتمال |
| التعافي | إعادة محاولة شبكة وبعض استراتيجيات المهارة | أخطاء 400 غير قابلة لإعادة المحاولة تحتاج تقليل قدرات الطلب أو تغيير نمط التوافق، لا مجرد إعادة الإرسال |
| الواجهة | لوحة حالة، مراحل، أدوات، وخطة | العرض كان يعرض حالة تاريخية ويحتاج فصل «النشاط الحي» عن «السجل» وطي التفاصيل |
| التشغيل المحلي | SQLite وSecureStore وإشعارات محلية | لا توجد آلية موحدة لاستئناف مهمة مقطوعة أو تسوية حالة مهمة بعد إغلاق التطبيق |

## ما الذي يجعل النظام توليفيًا اليوم؟

أولًا، الخطة والأحداث تُنتج من الكود قبل أن يثبت الوكيل أن الرسالة تستلزم تنفيذًا. هذا يجعل الواجهة قادرة على قول «أكتملت المهمة» بينما لم يحدث سوى رد نصي. ثانيًا، المهارة تختار أساسًا من خلال كلمات موجودة في النص، وليس عبر تصنيف نية مع حدود ثقة وأسئلة توضيحية. ثالثًا، أدوات قاعدة البيانات واسعة، لكن معظم العقود تظل وصفًا نصيًا للنموذج وليست schemas صارمة تُفحص قبل التنفيذ وبعده. رابعًا، طبقة المزود تحاول توحيد واجهات مختلفة بإرسال body واحد، وهذا لا يكفي عندما يختلف دعم الأدوات والبث ومعاملات التوليد من مزود إلى آخر.

## العقد المستهدف

يجب أن تصبح كل مهمة كيمو كائنًا محليًا مستقلًا، مثل:

```text
TaskRun
- id, sessionId, userRequest
- intent, skillId, confidence
- status: proposed | awaiting_user | running | verifying | completed | failed | cancelled
- planVersion, currentStepId
- startedAt, updatedAt, completedAt
- lastError, evidence
```

كل انتقال حالة يجب أن يكون حدثًا مسجلًا. لا يجوز الانتقال إلى `completed` إلا إذا وجدت نتيجة نهائية ورسالة تحقق أو دليل قراءة من قاعدة البيانات. ولا يجوز تنفيذ كتابة غير قابلة للتراجع أو ذات أثر واسع دون `approval` صريح أو سياسة تفويض محفوظة.

أما الأداة فيجب أن تعيد عقدًا موحدًا:

```text
ToolResult
- ok: boolean
- code: string
- summary: string
- data: unknown
- evidence: { entity, id, fields, readAt }[]
- retryable: boolean
- needsUser: boolean
- mutation: { kind, idempotencyKey, affectedIds } | null
```

## أولويات إعادة البناء

| الأولوية | العمل | معيار القبول |
|---|---|---|
| P0 | فصل حالة التشغيل عن أحداث العرض | لا تظهر لوحة مهمة دون `TaskRun` حي، ولا يعلن الاكتمال دون evidence |
| P0 | بوابة طلبات المزودات | كل طلب يمر عبر capability profile يحدد الأدوات والبث والمعاملات المدعومة |
| P0 | تحقق أدوات مركزي | الطلبات الناقصة أو غير الصحيحة تُرفض قبل SQLite برسالة مفهومة |
| P1 | مهارات تعتمد على نية وثقة | التحية والسؤال العام لا ينشئان خطة، والطلبات الغامضة تتحول إلى سؤال محدد |
| P1 | سجل تدقيق واستئناف | يمكن معرفة ما قُرئ وما كُتب وما تحقق منه، واستئناف المهمة بعد الإغلاق |
| P1 | واجهة نشاط صادقة وقابلة للطي | العنوان مختصر، والتفاصيل اختيارية، والحالة لا تختلط بسجل المحادثة |
| P2 | مصفوفة توافق المزودات | اختبارات contract لكل مزود ونموذج: نص، أدوات، بث، خطأ 400، timeout، وإعادة المحاولة |
| P2 | سيناريوهات عقارية مركبة | مشروع أرض، مبنى، تدفق نقدي، تفاوض، وعروض مرتبطة تنفذ وتتحقق دون تلف بيانات |

## قرار معماري

لن يكون الحل إضافة مزيد من التعليمات إلى prompt. سيتم اعتماد طبقات صريحة: `Intent Router`، ثم `Skill Policy`، ثم `TaskRun State Machine`، ثم `Tool Gateway`، ثم `Provider Adapter`، ثم `Local Evidence Store`. النموذج يقترح ويختار ضمن هذه الحدود؛ أما النظام فيتحقق ويفوض وينفذ ويسجل.

هذا الفصل ضروري حتى يظل التطبيق محليًا بالكامل: لا نحتاج إلى سحابة كي نملك حالة تشغيل موثوقة، لأن SQLite يستطيع حفظ المهمة والأحداث والأدلة والمعاملات محليًا. كما أن هذا الفصل يقلل الاعتماد على سلوك نموذج أو مزود بعينه، ويجعل تبديل الموديل عملية توافق مُختبرة لا مقامرة.

## معيار «جاهز للإنتاج» لكيمو

لا يُعتبر كيمو جاهزًا لمستوى عالمي حتى تنجح السيناريوهات التالية: رسالة عامة بلا خطة وهمية؛ إنشاء مشروع مع معاينة واعتماد وتحقق؛ تعديل جزئي لا يمس حقولًا أخرى؛ تسجيل دفعة مع إثبات دفتر النقد؛ إنشاء عرض وربطه بالعقار والعميل؛ سؤال توضيحي عند نقص البيانات؛ فشل مزود 400 مع تقليل الطلب أو شرح قابل للإصلاح؛ انقطاع الشبكة دون تكرار كتابة؛ وإغلاق التطبيق ثم استئناف المهمة دون ادعاء إنجاز غير مثبت.

هذه الوثيقة هي خط الأساس المعماري، وليست ادعاءً بأن التنفيذ اكتمل. الخطوات التالية يجب أن تبني العقد والبوابات والاختبارات تدريجيًا، مع إبقاء كل مرحلة قابلة للتشغيل محليًا.
