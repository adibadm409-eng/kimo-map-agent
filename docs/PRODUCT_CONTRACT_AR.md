# عقد المنتج والهندسة — مدير العقارات المحلي

## 1. هوية المنتج

التطبيق هو **نوته عقارية محلية مع هامش إدارة عقارية مركز**. يعمل على جهاز المستخدم، وتبقى قاعدة البيانات والملفات والمفاتيح تحت مسؤوليته. لا توجد مزامنة سحابية في هذه المرحلة، ولا يُفترض وجود مستخدمين متعددين أو صلاحيات فريق أو حسابات عن بعد.

هذا لا يعني أن التطبيق بدائي؛ بل يعني أن الجودة المطلوبة يجب أن تكون في **سلامة البيانات، وضوح التدفقات، قابلية الاستعادة، وقوة الأدوات المحلية**. التطبيق لا يعد المستخدم بحماية سحابية تلقائية، لكنه يجب ألا يضلله بشأن ما حفظه أو ما فشل في حفظه.

## 2. مبادئ غير قابلة للتفاوض

| المبدأ | التطبيق العملي |
|---|---|
| محلي بالكامل | لا نضيف API أو sync أو حسابات في هذه المرحلة؛ كل خدمة جديدة يجب أن تعمل دون شبكة باستثناء مزود LLM/خرائط اختياري يوافق عليه المستخدم |
| المستخدم صاحب القرار | كيمو يقترح ويقرأ وينفذ ضمن سياسة واضحة؛ لا يعلن نجاحاً من دون تحقق برمجي |
| مصدر حقيقة واحد | الكيانات المالية والعقارية لها services موحدة؛ لا تحسب الشاشة والوكيل نفس الرقم بطريقتين مختلفتين |
| البيانات قبل الذكاء | النموذج يساعد في الفهم والتحويل، لكنه لا يكون مصدر الحقيقة ولا يكتب SQL أو يقرر schema وحده |
| المعاملة قبل الدفعة | كل عملية مركبة إما تكتمل أو تُلغى؛ لا نترك مشروعاً نصف مستورد أو أقساطاً نصف مسجلة |
| الاستيراد قابل للمراجعة | كل إدخال يمر عبر معاينة، تطبيع، كشف تكرار، تقرير أخطاء، ثم commit واضح |
| المال غير قابل للتخمين | المدفوعات قيود ledger؛ المجاميع والحالات تستخرج منه، وأي فرق يظهر كتحذير لا يُخفى |
| الخصوصية المحلية | الأسرار خارج SQLite قدر الإمكان؛ لا تُرسل بيانات الأعمال إلى LLM إلا بسياسة وموافقة واضحة |
| واجهة مركزة | كل شاشة تقود إلى القرار التالي؛ لا قوائم زخرفية ولا أرقام ثابتة أو ألوان غير دلالية |
| التحقق الصادق | الفحص يختبر الناتج الفعلي والمسار الكامل، لا قصاصات مصدر أو افتراضات |

## 3. نموذج المجال الموحد

### 3.1 المشروع ليس قالباً واحداً

يجب أن يدعم النظام ثلاثة أنماط أولية من دون إجبار المستخدم على مصطلحات تقنية:

| نمط المشروع | التسلسل الطبيعي | البيانات الرئيسية |
|---|---|---|
| مشروع أراضٍ | مشروع ← بلوكات ← قطع | رقم القطعة، المساحة، القيمة، الحالة، الحدود، المشتري، المدفوع، المتبقي، الأقساط |
| مبنى سكني | مشروع/مبنى ← طوابق/مداخل ← وحدات | رقم الوحدة، الطابق، النوع، المساحة، السعر، الحالة، المشتري، الدفعات، الخدمات |
| برج/مجمع | مشروع ← مبانٍ/أبراج ← طوابق ← وحدات/مواقف/محلات | نوع الأصل، البرج، الطابق، الوحدة، المساحات، الاستخدام، البيع/الإيجار، التدفق المالي |

الطبقة المخزنة يمكن أن تبقى متوافقة مع الكيانات الحالية، لكن يجب إضافة **نوع المشروع، نوع العقدة، وترتيب العلاقة** حتى لا يضطر كيمو إلى تمثيل مبنى على أنه قطعة أرض.

### 3.2 الكيانات الأساسية

يجب أن تبقى كيانات `projects`, `blocks`, `plots`, `plot_payments` متوافقة مع البيانات الحالية، مع طبقة مجال جديدة تتيح:

- `project_kind`: `land`, `residential_building`, `tower`, `compound`, `custom`.
- `parent_id` و`node_kind` أو mapping واضح للعقد الهرمي عند الحاجة إلى طوابق ووحدات.
- `asset_code` كمعرف عرضي ثابت، مع منع التكرار داخل الأب.
- `status` موحد وقابل للتوسعة حسب نوع الأصل.
- `currency` على مستوى المشروع، مع افتراضي محلي قابل للتغيير.
- `source_batch_id` و`source_row_ref` لكل عملية استيراد.
- `created_by`, `updated_at`, `version` للتأكد من التزامن داخل الجهاز وتعارضات undo.

## 4. عقد إدخال المشاريع

أي جدول أو نص أو ملف يقدمه المستخدم لا يذهب مباشرة إلى قاعدة البيانات. يمر دائماً بهذه المراحل:

1. **اكتشاف النية:** هل البيانات أراضٍ، مبنى، برج، أم جدول حر؟
2. **قراءة المصدر:** قراءة جميع الأوراق/الأعمدة/العينات من دون تعديل.
3. **اقتراح المخطط:** عرض كيف ستتحول الأعمدة إلى مشروع وبلوكات وقطع/وحدات ودفعات.
4. **التطبيع:** توحيد الأرقام، التواريخ، العملة، الحالة، أرقام القطع، والهواتف.
5. **كشف التكرار:** مقارنة مفتاح الأصل داخل الأب، ومقارنة مصدر الصف، وبيان ما سيُتجاوز أو يُحدّث.
6. **معاينة قابلة للتصحيح:** عدد المقبول، المحذر، المكرر، المرفوض، والأعمدة غير المفهومة.
7. **التنفيذ الذري:** إنشاء دفعة import واحدة داخل transaction أو job قابل للاستئناف.
8. **التحقق:** مقارنة عدد المصدر بعدد الناتج، وفحص العلاقات والمجاميع المالية.
9. **تقرير نهائي:** يذكر ما أُدخل وما تُرك ولماذا، مع بطاقة فتح للمشروع.

كيمو لا يختار التوزيع أو الحالة بصمت عندما يكون ذلك مؤثراً مالياً. يسأل سؤالاً واحداً منظماً عند الغموض، ويستخدم افتراضاً معلناً فقط إذا كان آمنًا وقابلاً للتراجع.

## 5. عقد دفتر النقد والأقساط

الدفعة هي حدث مالي مستقل، وليست مجرد تعديل رقم على القطعة. كل دفعة يجب أن تحتوي، حسب المتاح، على المبلغ، التاريخ، الوسيلة، المستلم أو المرجع، الملاحظة، المصدر، ومن سجلها.

يجب أن تكون القواعد التالية مضمونة في service/database لا في prompt:

- المبلغ موجب ومحدود وفق سياسة المشروع.
- لا يسمح بتجاوز القيمة أو المتبقي إلا عبر عملية تصحيح موثقة.
- `paid_amount` و`remaining_amount` يعاد حسابهما من ledger.
- حالة الأصل تستنتج من المدفوع والبيع، أو يطلب النظام سبباً صريحاً للاستثناء.
- حذف الدفعة لا يكون حذفاً صامتاً؛ بل reversal أو إلغاء موثق.
- كل مشروع يملك ملخص قيمة، محصل، متبقٍ، نسبة تحصيل، فروقات، وأقساط متأخرة/مستحقة.
- أي فرق بين الأعمدة والدفتر يظهر كـ integrity issue ويمنع إعلان «البيانات سليمة».

## 6. عقد كيمو الجديد

### 6.1 طبقات كيمو

كيمو يعاد تنظيمه إلى طبقات مستقلة:

| الطبقة | الوظيفة |
|---|---|
| Intent Router | يحدد هل الطلب بحث، إدخال مشروع، تعديل مالي، تقرير، ملف، خريطة، أو سؤال عام |
| Skill Registry | مهارات الأعمال: تنظيم مشروع، استيراد جدول، تسجيل دفعة، مراجعة مشروع، إعداد تقرير |
| Planner | يحول الطلب إلى خطة قصيرة ومراحل قابلة للتنفيذ |
| Tool Policy | يحدد الأدوات المسموحة، حدودها، وهل تحتاج معاينة أو تأكيداً |
| Domain Services | ينفذ عمليات موحدة خارج النموذج: import, project, ledger, review |
| Verifier | يقرأ الحالة بعد التنفيذ ويقارنها بالعقد |
| Presenter | يشرح للمستخدم ما تم، ما لم يتم، وما يحتاج قراره |

### 6.2 مهارات كيمو الأولية

- **تنظيم مشروع أراضٍ:** تحويل جدول إلى مشروع/بلوكات/قطع مع preview وتحقق.
- **تنظيم مبنى أو برج:** اكتشاف الطوابق والوحدات والمواقف والمحلات دون خلطها بالقطع.
- **تعبئة بيانات أصل:** تحديث الأصل الموجود بدلاً من إنشاء نسخة مكررة.
- **تسجيل دفعة:** اختيار المشروع/الوحدة/القطعة، التحقق من المتبقي، إنشاء ledger entry، وإظهار إيصال داخلي.
- **مراجعة مالية:** مقارنة قيمة الأصل، المدفوعات، المتبقي، والفروقات.
- **مراجعة جودة مشروع:** كشف السجلات الناقصة، أرقام مكررة، علاقات مفقودة، ومبالغ غير متسقة.
- **استيراد ملف:** معاينة، تطبيع، كشف تكرار، commit، وتقرير.
- **إنشاء تقرير:** KPI، دفتر دفعات، متأخرات، قائمة أصول، وتصدير محلي.
- **إدارة المرفقات:** ربط المرفق بجلسة/مشروع واضح وعدم الاعتماد على الاسم فقط.

### 6.3 قاعدة استخدام الأدوات

لا يستدعي كيمو أدوات CRUD العامة عندما توجد أداة مجال مناسبة. إدخال مشروع يستخدم `project_import_preview` ثم `project_import_commit`، وتسجيل الدفع يستخدم `ledger_record_payment`، والمراجعة تستخدم `project_integrity_check`. أدوات CRUD العامة تبقى للعمليات الصغيرة الواضحة فقط.

كل أداة مجال يجب أن تكون:

- typed input/output مع schema قابل للتحقق.
- idempotent أو تحمل `operation_id` يمنع التكرار.
- محلية ومباشرة، ولا تسمح للنموذج بكتابة SQL.
- تعيد `status`, `affected`, `warnings`, `errors`, `verification`.
- قابلة للإلغاء قبل commit، وقابلة للمراجعة بعد commit.

## 7. وضعا التشغيل

| الوضع | سلوك كيمو |
|---|---|
| قراءة ومراجعة | يقرأ ويحلل ويقترح ويولد ملفات؛ لا يغير قاعدة البيانات |
| تنفيذ موجه | يطبق عمليات مع preview للدفعات والتغييرات الحساسة، ثم commit صريح |

التبديل إلى التنفيذ لا يمنح صلاحية غير محدودة؛ كل عملية جماعية لها حد حجم، وpreview، ونتيجة تحقق. الحذف والتسويات العكسية تحتاج تأكيداً مستقلاً.

## 8. تعريف الجاهزية

لا تعتبر النسخة إنتاجية محلياً قبل تحقيق الآتي:

- يمكن إدخال مشروع أراضٍ بمئات القطع من جدول، معاينته، استيراده مرة واحدة، وإعادة الملف دون تكرار.
- يمكن إدخال مبنى أو برج مع طوابق ووحدات من دون تحويلها إلى كيانات خاطئة.
- يمكن تسجيل دفعات وتصحيحها وإلغاءها مع دفتر قابل للمراجعة، ولا تظهر أرقام متضاربة.
- يستطيع كيمو تنفيذ المهارات السابقة بأدوات مجال، ويرفض أو يسأل عند الغموض.
- النسخ والاستعادة تعيدان البيانات والملفات وفق manifest وتكشفان النقص.
- لا تحفظ مفاتيح LLM في SQLite، ولا تدخل في backup غير مشفر.
- توجد اختبارات integration وagent contract وbackup round-trip وimport fixtures داخل CI.
- كل شاشة رئيسية تعمل في RTL وdark mode وfont scaling، وتعرض loading/error/empty states حقيقية.

هذا العقد هو المرجع عند تعارض تحسين صغير مع سلامة البيانات أو وضوح تجربة المستخدم.
